# Скрипты проекта

Все команды запускаются из корня проекта: `python src/<имя_файла>.py`.
Рабочие файлы аудита находятся в корневой папке `audit/`.

## Подготовка

```powershell
pip install -r requirements.txt
ollama pull gpt-oss:20b
ollama pull bge-m3:latest
```

Для запросов к моделям нужен работающий сервер Ollama. Аддрес настраиваетсяв config.py. Там же можно поменять embedding-модель. В качестве LLM выступает gpt-oss:20b, ее нет в конфиге, но можно поменять в коде. Причина: используется парсинг `<think> .. </think>` размышлений этой модели, который может сломаться при подключении другой.

## Что делает код в src

| Файл | Назначение |
|---|---|
| `load_data.py` | Загружает GSM8K, конфигурацию `main`, и сохраняет `train.csv` и `test.csv` в `data/dataset/`. |
| `sampling_for_labeling.py` | Последовательно решает задачи из `train.csv` через `gpt-oss:20b`, собирая до 75 примеров каждой метки Exact Match. Записывает CSV со случайным именем в `data/labeling/`, добавляет колонку «ручная проверка» со строкой `null`. |
| `evaluators.py` | Содержит Exact Match, разделение `<think>` и решения, а также LLM-оценщик. Это модуль с функциями, отдельного запуска нет. |
| `make_slice_json.py` | Из `data/labeling/selected_tasks.csv` выбирает первые подходящие примеры: по 10 каждой метки в `core`, затем по 16 в `second`. Создаёт `audit/slice.jsonl`, всего 52 примера. |
| `fill_by_exact_match.py` | Заполняет `verdict` в `audit/baseline_predictions.csv` сохранёнными метками из `selected_tasks.csv`. Сопоставляет строки по ID. |
| `run_llm_evaluator.py` | Оценивает исходный срез через LLM и создаёт `audit/scorer.jsonl`. Сохраняет каждый результат, может продолжить прерванный запуск. |
| `break_predictions.py` | Создаёт два изменённых среза для зондов. Получает и кеширует эмбеддинги в `selected_tasks.csv`. |
| `check_exact_match_robustness.py` | Проверяет оба зонда через Exact Match и LLM, считает две метрики и добавляет строки в `audit/probe_results.csv`. |

## Данные

После сбора примеров выберите нужный CSV и сохраните его как
`data/labeling/selected_tasks.csv`. Сборщик сам не переименовывает его.

Поля в `slice.jsonl`: `id`, `group`, `question`, `model_thinking`, `model_answer`,
`reference_answer`. В `model_answer` находится решение без `<think>`,
в `model_thinking` — содержимое этого блока, в `reference_answer` — полный эталон.

ID имеют вид `K09-027`, где О27 означает 27-ю запись из selected_tasks.csv (без заголовка).

## Оценщики

`exact_match(model_answer, reference_answer)` сравнивает только числа после
последнего `####`. Нормализует пробелы, разделители тысяч, знак минуса и
десятичную запись. Например, `42` и `42.0` совпадают. Без `####`, с ответом
словами или некорректным числом возвращает `False`. Ход решения не проверяет.

`LLM_as_evaluator(math_task, solution, reference_solution)` использует
`gpt-oss:20b`: проверяет объяснение, промежуточные вычисления и итоговый ответ,
разрешает альтернативные корректные способы решения. Возвращает `bool`.
Блок `<think>` ответа исключается из проверки. Ошибки API и неверный формат ответа
вызывают исключения, а не превращаются в `False`.

## Зонды

Константа `BROKEN_FRACTION = 0.5` в `break_predictions.py` задаёт долю
изменяемых примеров. Берутся первые `int(число_примеров * доля)` записей:
для текущего среза это 26 из 52. Остальные записи остаются прежними.

1. `slice_broken_1.jsonl`: финальное число после `####` переводится в английские
   слова через `num2words`. Ход решения сохраняется.
2. `slice_broken_2.jsonl`: ход решения заменяется ближайшим по косинусному
   сходству ходом решения из `selected_tasks.csv`. Совпадения с текущим решением
   пропускаются с учётом нормализации пробелов.

## Проверка зондов и probe_results.csv

Проверка определяет изменённые примеры сравнением `model_answer` с исходным
срезом по ID. Неизменённые примеры не оцениваются повторно. Исходные вердикты
Exact Match читаются из `baseline_predictions.csv`, LLM_evaluator — из `scorer.jsonl`.

Для каждого зонда и каждого оценщика рассчитываются:

| `metric` | Формула `value` | Значение `n` |
|---|---|---|
| `acceptance_rate_delta` | `(число True после − число True до) / N` | Все проверенные изменённые примеры. |
| `true_to_false_rate` | `число переходов True → False / число исходных True` | Исходно принятые среди изменённых примеров. |

Если исходных `True` нет, вторая метрика не определена и соответствующая строка
не добавляется. Дельта может быть отрицательной. Эти метрики описывают изменение
вердиктов, а не точность относительно человеческой разметки.

Итоги записываются в столбцы `probe,n,metric,value,interpretation`:

- `probe` содержит зонд и оценщик, например `answer_in_words/exact_match`
  или `swapped_reasoning/LLM_as_evaluator`;
- `n` — знаменатель соответствующей метрики;
- `value` — число без знака процента;
- `interpretation` остаётся пустым для ручного заполнения.

Обычно один успешный запуск добавляет **8 новых строк**. Предыдущие строки
сохраняются. Каждый повторный успешный запуск снова добавляет результаты,
даже если они совпадают с предыдущими.

LLM-вердикты на изменённых примерах сохраняются после каждого ответа в
`audit/scorer_broken_1.jsonl` и `audit/scorer_broken_2.jsonl`. Эти файлы содержат
ID, булевый вердикт и хеш входных данных. После прерывания проверка продолжится
из кеша; если вход изменился, соответствующий пример будет оценён заново.
После изменения модели или промпта оценщика удалите оба кеша вручную.
Итоговые строки CSV добавляются только после успешной проверки обоих зондов.
